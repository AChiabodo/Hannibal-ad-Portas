# A Match in a browser ends at its bound

The page's Match runs to the same horizon as every other Match — `MATCH_TICKS`, three game years, 25 200 ticks, forty-two minutes of Match time — and the page says so: `bound()` is the tick it ends on, `result()` is how it ended, and the frame loop stops on the tick it ended on rather than playing a finished world into the night. Until E4 the page's Match had no end at all, because the glossary's rule was that a *human* Match has no limit on its years and only a headless one is bound; that rule cannot survive an inspecting agent, and it did not survive the ticket that added one.

What E4 asks for is a Match that can be **played to its end from outside the page**, by a test or by an agent driving the browser. A Match that never ends is exactly the thing that cannot be. So the bound moved from "a property of a headless run" to "a property of a Match": `MATCH_YEARS` and `MATCH_TICKS` in `sim/season.ts` are the game's own numbers now, `HEADLESS_YEARS` and `HEADLESS_TICKS` are the same two under the names the CLI's arguments read them by, and `render/game.ts` plays to them with a `requestAnimationFrame` loop that a browser test skips with `fastForward()`.

`fastForward()` **skips** the wall clock rather than accelerating it: the frame loop is not asked to run faster, the ticks are stepped as fast as the rules allow, and the answer is the rules' and not the frame rate's. That is the difference between a fast-forward a test can assert on and a `setSpeed(3)` a demonstration can watch: the pace changes how much wall time a tick costs, and every frame rate in the world changes what that costs in practice. Because the ticks are the same ticks, a Match fast-forwarded in a browser ends on the same state hash as the same Match played slowly — which is the property that makes the browser suite's evidence worth reading.

**Considered Options**: leaving the page's Match unbounded and giving the test a shorter Match to play — rejected because it would have meant a second way to open a Match in the page (a restart, a re-muster, a re-fogged theatre) and a second set of code paths to keep honest, in service of a test rather than of the game. Ending the browser Match at a *shorter* bound than the CLI's — rejected: two answers to "how long is a Match" is how a browser Match and a headless Match stop being the same Match. Accelerating the existing loop for the test instead of skipping it — rejected because a test that waits on a frame rate is a test that fails on a slow runner. Announcing the end in the HUD — deferred rather than rejected: the page's Match has an economy and no Siege, so nothing can be won in it and its only ending is the clock, and "the interface says the Match is over" is the interface's ticket, not this one. The hooks report the ending today; the panels will say it when they have a verdict worth announcing.

**Consequences**: the glossary's *Year* now says a Match is bound to three game years and that a caller may hand over another bound; the page's Match and the CLI's default are one number. `advance()` refuses to step past the bound rather than clamping, so a caller that wants the end asks for it by name (`fastForward`) and a step that would overshoot is a loud mistake instead of a silent half-step. A Match that has ended answers a second `fastForward()` with the ending it already had, and `start()` will not restart the loop over it. CI plays the whole Match in headless Chromium — boot, an order, and 25 200 ticks in about a second — which is what `e2e/match.spec.ts` is. The end is not drawn in the interface yet, and that is the one piece of this decision a later ticket owns.
