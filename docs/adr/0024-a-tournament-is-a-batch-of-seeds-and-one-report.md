# A tournament is a batch of seeds and one report

A **tournament** is N AI-vs-AI Matches on N distinct seeds, played at one difficulty and one bound, reduced to **one JSON report**: `npm run tournament`, and the plan's definition of a balanced game — a win rate between 45% and 55%, a median duration of 25 to 45 minutes, under 5% of Matches decided by the clock (PLAN §5, DoD 5) — is measured by it. The report states each Faction's wins and win rate over the whole batch, how long a Match lasted as percentiles of it (in ticks and in game minutes), how many Matches and what share of them the clock ended, every Match of the batch by seed, and the seeds of the Matches that were lopsided or stalled.

**The report is a function of the seeds and the build, and of nothing else.** It carries no timings, no paths, no wall clock and no generated-at line, for the reason a Match's own report does not: two runs of the same batch on the same build must print the same bytes, so a later ticket can gate on the report and a reader can diff this week's against last week's and see only what changed in the game. The decision logs are not in it — one Match's is some twenty megabytes of JSON — and neither is the directory they were written to, so the report does not even depend on whether they were kept. That a batch of independent Matches is spread over the machine's cores and the report does not move a byte for it is a test, not a hope.

**The Matches run on the machine's other cores.** Two hundred Matches of up to three game years is about half an hour of simulation on one core and four minutes on twelve, which is the difference between "the balance number" and "an overnight job" — and the plan said as much when it chose ten hertz (PLAN §3, §6). `worker_threads` is the only place in this project that knows a machine has more than one core, and each thread plays one Match at a time from one counter until the seeds run out. Distributed execution is out of scope, and is not needed: the batch is embarrassingly parallel, and one machine has enough cores to make it a coffee break.

**The report measures and does not judge.** It states the DoD's numbers and does not say whether they were met: F1 is the ticket that decides what to do about them, and a report that also judged would make F1's first job auditing the judge. Every percentile is nearest-rank, so every duration in the report is a duration some Match actually had, rather than a median of 26.5 minutes that no Match lasted. The outliers are named classes with stated rules rather than "look at the distribution": **stalled** is a Match the clock ended, because no Faction could win it; **lopsided** is a victory that was not a contest — won in at most half the batch's median duration, or won outright, leaving the loser neither settlement nor Squad. Duration alone would miss the most complete defeat a Match can be and report "nothing to see" about it, which is the one reading a balance discussion must not be given by its own instrument. Both are listed with their seeds, because the seed is how a Match is looked at again.

**A Match's decisions are retrieved, not carried.** The two mechanisms are the same document: `--keep` writes it now, and `npm run match -- --rules ai --seed <seed> --difficulty <level> --ticks <bound>` writes it later, because a Match is a seed and a build. That is why `npm run match` gained `--difficulty` in this ticket, and why the report states the level and the bound it played at rather than assuming the engine's baseline: a batch at Tiro whose Matches could only be replayed at Centurio would be a report whose decision logs cannot be retrieved, which is one of the ticket's criteria. The flag is refused beside any `--rules` that has no AI in it, because a level that changed nothing about the Match would be a flag that lies. `--keep <dir>` writes, per seed, the very report `npm run match -- --rules ai --seed <seed>` prints for that Match — decisions, candidates, utilities and all — named after its seed by a rule rather than by a path in the report. Without `--keep` a Match is retrieved the same way, from the seed the report names, and its `hash` is what proves the Match retrieved is the Match measured (ADR-0023). A Match that cannot be played stops the batch, naming its seed: a balance number computed over a sample that silently shrank is not a measurement. The command exits 0 however the game turned out — a report is a measurement — 1 for a Match that could not be played, and 2 for a command line that could not be run.

**Considered Options**: playing the batch one Match at a time — rejected as the default, because an hour per balance number is the overnight job the ten-hertz tick exists to avoid; it stays available as `--workers 1`, and is what the report's invariance is tested against. One process per Match instead of a thread — rejected: loading this project's module graph costs more than a short Match, and a hundred Matches would pay it a hundred times. Writing every Match's decision log by default — rejected: four gigabytes is not a report. A compact, sampled decision log instead — rejected: the log is the AI's own document, every candidate and every utility, and trimming it belongs to a ticket about the AI. Interpolated percentiles — rejected: they invent durations no Match had. A verdict against the DoD thresholds inside the report — rejected: it makes the judge part of the instrument. Seeding the batch from the clock, so `--seeds 200` picks a new sample each time — rejected: a batch nobody can run again is not a measurement, and the seeds are the whole of what a batch is. Putting the seeds' decision logs on standard error or in the report — rejected: one is a stream for failures and the other is a document that must stay small and diffable.

**Consequences**: the batch also found the game's own hot spot, and fixing it is part of this ticket: a Match spent most of its time in `ai/scouting.ts` walking the whole theatre for frontier ground on every tick, and `cli/ai-match.ts` asked it for the same patrols twice per tick for two different callers. Computing the frontier once per theatre per call, and planning the patrols once per Observation, cut a Match's cost by about two and a half times and changed no decision — the same state hashes, the same Command logs, the same decision logs, which is what the batch was measured against before and after. Without it the batch above would have taken eleven minutes rather than four, and the ten-hertz tick's own reason — a balance tournament that is a coffee break — would not have held. `cli/tournament.ts` owns the report — `MatchSummary`, `TournamentReport`, `tournamentReportOf`, `formatTournamentReport` — and its arithmetic, which is a pure function of a list of summaries and the batch that produced them. `cli/tournament-batch.ts` owns playing a batch: `runTournament`, the worker pool, and `playTournamentMatch`, the one function a thread runs. `cli/tournament-worker.ts` is a message handler around that function. `cli/tournament-arguments.ts` and `cli/tournament-main.ts` are the command, and `npm run tournament` is it; `package.json` gains the script. `ai/difficulty.ts` gains `DIFFICULTY_NAMES` and `isDifficultyName`, so `--difficulty` refuses an unknown level by name and the list it quotes is the table's own. The report is what F1's balance pass reads, and what any later work gates on.
