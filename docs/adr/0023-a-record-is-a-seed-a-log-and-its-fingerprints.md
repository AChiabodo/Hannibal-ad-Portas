# A record is a seed, a log, and the fingerprints that verify it

A Match is recorded as **a seed, a Command log, and the state hash of every checkpoint the run passed through** — one small JSON file, `npm run match -- --record <file>` or `npm run agent -- --record <file>`, and `npm run replay -- <file>` runs it again. There is no video and no state snapshot: the seed and the log reproduce the Match, and the fingerprints are what turn "it ran again" into "it ran again *exactly*, and it was the same Match until tick 3400".

A **divergence** is a first-class outcome and not an error message. A replay compares its own checkpoints against the record's and reports the first tick whose two hashes disagree, quoting both, together with the last checkpoint the two still agreed on. That second tick is what keeps the report honest: checkpoints are taken at an interval, so the runs were already different somewhere in the window, and the window is the reader's to see rather than the report's to hide. A rule change is supposed to produce this report — it is the instrument the ticket exists for — so the command prints the report and then exits 1, exactly as a violated `--expect-hash` does.

The interval is `CHECKPOINT_TICKS`, one game second, and it is written into the file rather than assumed by the reader. Hashing is the expensive half of a replay: `hashState` serializes the whole world, so a three-year Match fingerprinted every tick would spend longer hashing than simulating, and its record would be half a megabyte of hashes — which is not the file that gets attached to an issue. One second makes an agent's whole Match some thirty kilobytes, a three-year Match that ran to its bound about a hundred and sixty, and the longest of them replays in about ten seconds — a file that attaches to an issue either way. The field being in the record means a later ticket can choose differently without changing the format.

The **ending** is derived again, not repeated. The hashes cover the world and the world does not contain its own ending: "is this Match over" is a question about the world *and* the rules, so a rule that changes when a Match is decided — a victory that now needs two breaches, an annihilation that now counts a garrison — leaves every checkpoint identical and only the ending different. A replay therefore asks each name's own `outcome` the way the driver asks it, once per tick, and records the *first* tick that decided; a clock ending is the absence of one by the bound. That derived `MatchResult` is compared to the record's, and a mismatch is a departure of its own kind, reported in the words a Match's own report uses. It is the class of rule change that neither `--expect-hash` nor the checkpoints can catch, and E2 names it: *a Match that ended by clock expiry replays to the same ending*.

**Considered Options**: echoing the record's ending instead of deriving it — rejected because it makes the criterion vacuous: a report that repeats what the record says cannot disagree with it. Stopping the replay at the first decision the rules give — rejected as noise: the point of a replay is to compare checkpoint for checkpoint, so a build that would end a Match sooner is reported as an ending departure at that tick while the run carries on to the tick the record ended at. Deriving the ending only at the final checkpoint — rejected: a Match decided *earlier* still reads as decided at the end, which is the change a rule edit most often makes. Recording full state snapshots per checkpoint — rejected outright: the state is the whole theatre, and a record of it would be megabytes, unreadable, and no more verifiable than sixteen hexadecimal digits. Fingerprinting every tick — rejected as the default for the cost above, and kept as a number in the file for whoever needs it. Comparing only the final hash, so a record is nothing but a seed and a log — rejected because "something differs" is not a bug report: the ticket asks for the first tick that differs, which needs a fingerprint per checkpoint and not one at the end. Treating a divergence as a broken command line and exiting 2 — rejected: the command line was fine, and the news is about the build. Letting the replay deduce the rules from the log — rejected: a log records what was *ordered*, not the matrix it was ordered against, and a record whose Match is a guess is a record nothing can be compared with. Recording by making the driver hash as it goes — rejected for now: it moves a harness concern into the loop every Match runs, and recording a Match by replaying it once is also the moment a Match is checked against itself, which is why a record that does not replay is never written at all.

**Consequences**: `sim/replay.ts` gains `divergenceOf`, the one comparison of two checkpoint lists, and `Divergence` is a value rather than a message; its `replay` gains an optional `outcome` hook and reports the ending it reached and the hash it ended on. `sim/outcome.ts` is where `Outcome`, `MatchResult`, `VictoryReason` and `sameEnding` live — the verdict is not about driving a Match, and a replay needs it — and `sim/driver.ts` re-exports them so no caller had to move. `cli/record.ts` owns the file — `recordOf`, `formatRecord`, `readRecord`, `writeRecord`, `readRecordFile` — and it reads what it wrote the way a Command from outside is read: every field checked, unknown fields refused by name, checkpoints required to be the schedule a run keeps. `cli/replay.ts` owns the verdict, `DivergenceError` and the report, `cli/replay-main.ts` is the command, and `npm run replay` is it. Every name in `cli/rules.ts` carries a `replay` closure beside its `play`, because a name is not only rules — the march, roster and attrition Matches muster armies onto the seed's theatre — and a replay that started from the bare economy world would part from its record at tick zero; the table's test replays every name to prove it. The agent harness files its Matches under `siege`, the bare theatre, because a record names the rules and not the Players: the process that decided is gone, and the log is the whole of what it contributed. `--log` stays as it was, the Commands and nothing else, and `--record` is the form a replay reads.
